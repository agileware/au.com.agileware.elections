# Git and pull requests

How changes get into the extension: branches, commits, pull requests, the required checks and review, and what a database change must include. The short list of rules is in [`AGENTS.md`](../../AGENTS.md); [`CONTRIBUTING.md`](../../CONTRIBUTING.md) covers tests, templates, wording and releases. This page is the longer version.

## Branches

| Branch | What it is | Who changes it |
|---|---|---|
| `master` | The next release. It holds the latest release plus anything merged since. Protected. | A pull request only. Nobody pushes to it. The Cut release workflow (the Actions bot) cannot push its docs commit |
| `release` | The released tree: `master` with the development files removed. It is what tags point at and what the CiviCRM extension directory installs | Only the Cut release workflow, which resets it to the filtered tree each time. Never edit it by hand |
| Version branches, for example `version-2.1`, `version-2.2` | The work for one release, cut from `origin/master` | The developers of that release |
| Topic branches, for example `developer-docs` | One piece of work (the developer guide), cut from `origin/master`, merged by pull request | The author |

Rules:

- Cut a new branch from the current `origin/master` (`git fetch --all --tags` first), not from an old local `master` or from an earlier version branch. Release 2.1.0 was the squash of `version-2.1` into `master`, so that branch is history.
- Name a version branch `version-<major>.<minor>`. Ask the maintainer for the name and whether the branch is pushed as it goes. The rule "kept local until every item is done, then one release pull request" applied to 2.1 only; do not assume it for later versions.
- Old branches called `backup*` or `backup/*` are history. Do not build on them.
- Never push to `master` and never force push a shared branch.

## Commits

- **Short and descriptive**, one change per commit, in the imperative: "Add option to hide candidate photos (#44)". The first line says what changed, not how.
- **Reference the GitHub issue** where there is one, as `(#44)`, so a release can comment on and close each issue and cite its commits.
- **No AI or assistant attribution** in commits or pull request text: no `Co-Authored-By` line for an assistant and no "generated with" line. A real contributor's work keeps their name (cherry-pick it, do not rewrite the author).
- Keep generated and large files out of commits. Never commit passwords, personal links, API tokens or machine paths. The test sites' credentials are generated by scripts and stay out of the repository; see [`../testing/seeding.md`](../testing/seeding.md).
- Keep wording changes on their own commit when they touch many files, so the other diffs stay readable.

## Pull requests

- Open a pull request from your branch to `master`. Do this only when the maintainer says so; pushing, opening or merging a pull request, running Cut release and changing GitHub settings are all outward-facing and wait for a go-ahead.
- **The description lists the features and changes only** (and housekeeping such as workflow or documentation changes). It does not describe testing or environments, and it carries no AI attribution. Link the issues it closes (`Closes #44`).
- Paste the checklist from [`ui-standards.md`](ui-standards.md#14-checklist-for-reviewing-a-pull-request) into the description when a screen or a message changes, and tick what applies. There is no pull request template in the repository yet (the decision to add one is open; see [`../decisions/README.md`](../decisions/README.md)).
- Keep a pull request to one purpose and one release.

### Checks and review

`master` is protected by a ruleset. A pull request must have:

- **One approving review**, of the most recent push, with every conversation resolved. Merge, squash and rebase are all allowed.
- **Three required status checks**, each from a workflow in `.github/workflows/` that calls a reusable workflow in `agileware/ci-workflows`:

| Check | Workflow file | What it runs |
|---|---|---|
| `phpunit / phpunit` | `phpunit-tests.yml` | The headless PHPUnit suite (`tests/phpunit`) against WordPress and the newest stable CiviCRM the pipeline image carries |
| `upgrade / upgrade` | `upgrade-tests.yml` | Installs the last 1.x release (`FROM_REF: 1.3.2`), seeds elections in every stage, upgrades to the commit under test and verifies nothing was lost (`tests/upgrade`) |
| `playwright / playwright` | `frontend-tests.yml` | The Playwright browser suite on WordPress, using `tests/playwright/fixtures/setup-environment.sh` |

These run on every push to `master`, on every pull request and by hand (`workflow_dispatch`). Drupal and Joomla are not in CI: run their Playwright suites locally before any change that touches a screen (see [`../testing/README.md`](../testing/README.md) and [`../testing/ci.md`](../testing/ci.md)). The workflows call the shared workflows at `@main`; a re-run of an earlier run keeps the shared workflow version it first used, so start a new run to test a change there.

Also:

- The rules block deleting `master` and force pushes to it.
- Test on **both CiviCRM 6.16 and 6.19**. They behave differently (6.19 hides AJAX error messages unless a `CRM_Elections_Exception` is thrown, and needs `is_public` for front end pages). See [`../testing/cms-and-civicrm-differences.md`](../testing/cms-and-civicrm-differences.md).
- Test every changed screen as the people who use it, on all three CMSs; see [`../testing/personas.md`](../testing/personas.md).
- Run long test jobs in the background with a log file; never run two jobs on one site, and do not deploy during a run.

## Database changes

Any new or changed table, column or index must ship with all of these in the same pull request, so existing installs upgrade:

1. **The schema definition** in `schema/<Entity>.entityType.php`.
2. **An upgrade step** in `CRM_Elections_Upgrader`, named `upgrade_2xxxx`, with the next free number above the last step. The last step in the code is `upgrade_20130`, so **the next free number is `20140`** (the Senate count work is planned to start there). Steps must be safe to run twice: use the `ensureColumn()` helper, or check `information_schema` before adding a key, and give foreign keys an `ON DELETE` rule.
3. **A test in `UpgraderTest`** (`tests/phpunit/CRM/Elections/UpgraderTest.php`) that runs the step on a database without the change. The test is not transactional (upgrade steps change the schema), and its `tearDown` re-runs every step so the shared test database ends with the full schema; add yours to that list.
4. **Every place that lists columns by hand**: a `SELECT` that feeds an object, the audit field list (`CRM_Elections_Helper_Guard::AUDITED_ELECTION_FIELDS` for elections), the Duplicate actions and the guard that freezes started elections. A column missed in a hand-written `SELECT` once caused "Undefined property".
5. **The 1.3.2 upgrade test**: `tests/upgrade/` must still pass (and `verify-v2.php` checks the result). See [`../testing/upgrade-test.md`](../testing/upgrade-test.md) and [`../architecture/upgrades.md`](../architecture/upgrades.md).
6. **Documentation and wording**: user-facing words follow [`wording.md`](wording.md) and the labels in [`ui-standards.md`](ui-standards.md); `docs/` is updated to the new screens.

Remember that the headless test database does not follow upgrades by itself: after a schema change, rebuild it from the site database before running PHPUnit on a DDEV site (CI builds it new each time).

## Releases

Releases are cut by the **Cut release** workflow (`cut-release.yml`) from `master`, not by hand. In short: set `<version>` and `<releaseDate>` in `info.xml` on `master` through a pull request, then run the workflow with the same version. It removes `.github`, `tests`, `.gitignore`, `CONTRIBUTING.md`, `developer` and `AGENTS.md` from the `release` branch, tags it and publishes the GitHub Release. Do not tag or run it unless the maintainer asks. The full procedure, the branch rules and what ships are in [`../releases/README.md`](../releases/README.md) and [`../releases/branches-and-rules.md`](../releases/branches-and-rules.md).

When a release is out, comment on and close each GitHub issue it resolves, citing the commits, and record the decisions made along the way in [`../decisions/`](../decisions/README.md).
