## R1 – Manage Elections filters

**Today.** `ang/afsearchManageElections.aff.html` has two filters, **Election** (text) and **Active** (yes/no), with no explanation. The table already holds the dates, so date filters need no new data.

**Proposal.**

## R2 – No modifying buttons on an active election

**Today.** The Manage Elections row shows Activate/Deactivate, Positions, Candidates, Edit, Duplicate and Delete for every election. Edit and Delete are refused by the server for an active election, but the buttons are still offered. Deactivate is allowed by the server at any time, and an inactive election can be edited again, so Deactivate on a running election is a back door around the lock (audit logged, but still).

**Proposal.**
- Add one computed column to the search, `Locked` = `IF(is_visible = 1 AND nomination_start_date <= NOW(), 1, 0)` (APIv4 has `IF` and `NOW`; both exist in 6.16 and 6.19). It is also what the positions page choice in R3 can reuse, and the Stage column in R1 is built the same way.
- Row buttons, by state:
  - **Not active** (not switched on, or nominations not started): Activate, Positions, Candidates, Edit, Duplicate, Delete – as today.
  - **Active**: Positions (opens the read-only view, R3), Candidates, Duplicate. No Edit, no Delete, no Deactivate.
- A small "Locked" badge with a tooltip in the Election column: "This election is active, so it cannot be changed."
- Server rules stay as they are. If we hide Deactivate, an administrator who started an election by mistake has no way to pull it from view. Two ways to cover that: (a) a separate "Withdraw election" action that needs the administrator to type the election name and writes an audit entry, or (b) leave Deactivate visible but with a confirmation that spells out the consequence.

**Approved 31 October (all three recommendations: hide Edit and Delete; hide Deactivate and add a confirmed Withdraw; keep "Active" and add "Locked").** Questions as asked:
1. Hide Edit and Delete on an active election – yes? *(Recommended: yes.)*
2. Deactivate on an active election: hide it, show it with a warning, or hide it and add a confirmed "Withdraw election"? *(Recommended: hide it and add Withdraw; it is a small action and it closes the back door.)*
3. Naming: keep "Active" as the label of the switch (it means "switched on"), and call the new state "Locked" in the interface and "active" only in running text? Or rename the switch to "Published"? *(Recommended: keep "Active", add "Locked".)*

**Tests and docs.** Playwright against election-test elections in each stage (1 nominations, 2 voting, 3 advertise, 8 results; plus an inactive started one made by `ddev move-election`). Update `docs/admin_manage_elections.md`, `admin_edit_election.md`, `admin_activate_election.md`.

## R3 – Positions page on an active election

**Today.**
- `ang/afsearchElectionPositions.aff.html` always shows the Add Position button, the help text and a table with `draggable`, inline edit and Duplicate/Delete.
- Server side, `GuardsStartedElections` correctly refuses the write ("Election position cannot be added/modified once election has been started."). Duplicate shows that message. The drag does not: SearchKit reports a generic "Sorry an error occurred ... (Error ID ...)". I have not yet found why the exception message is lost on that path (it goes through APIv4 `save`, not the form). It must be reproduced first (Playwright with a started election) and fixed at the source so every write path gives the real message.

**Proposal.**
1. **Separate read-only display and page.** New `ElectionPositionsLocked` search display (same saved search, no `draggable`, no `editable`, no buttons) and a second Afform page, `civicrm/elections/position-list-active`, with:
   - no Add Position button;
   - a heading note instead of the drag help text: "The positions of this election are listed below. They cannot be changed while the election is active.";
   - Back to Manage Elections only.
2. **Choosing the page.** The existing route `civicrm/elections/positions` is already a PHP page that redirects to the list. It decides: active election goes to the read-only page, any other goes to the editable one. The Manage Elections links (button and count) point at `civicrm/elections/positions`.
3. **Safety net for old links and open tabs.** The editable page can still be opened directly (a bookmark, or a page left open while the election starts). Its writes stay refused. We make the message right: drag, inline edit, Duplicate and Delete all return the same explanatory text: "This election is active, so its positions cannot be changed. Positions can be changed only before nominations start, or while the election is switched off." (and the SearchKit error shows it instead of the generic text).
4. If the election becomes active while the editable page is open, the next write shows that message and a link to the read-only page.

**Alternative.** One page that turns drag and edit off from the election's state (a custom display setting). It cannot be done with plain SearchKit settings (they are static), so it needs custom Angular code. Not recommended.

**Approved 31 October, including the wording in point 3.** Question as asked: go with the separate read-only page chosen by the `civicrm/elections/positions` route, plus the clearer message everywhere? *(Recommended: yes. The wording in point 3 is also for your approval.)*

**Tests and docs.** PHPUnit for the message on every write path; Playwright for the redirect, the absence of controls and the heading text, and for drag on a stale editable page showing the clear message. Update `docs/admin_reorder_positions.md`, `admin_add_position.md`, `admin_edit_position.md`.

- Translation: changed strings are new msgids; there are no shipped translations to migrate.

## R6 – Date calculator

**Rules to respect.** Eleven ordering rules in `getDateRules()`: nominations start after the visibility start; each stage starts after the previous one ends; everything must end before the visibility end. Dates are in the site time zone (`CRM_Elections_Helper_TimeZone`).

**Proposal.** A panel at the top of the Dates tab, "Quick set-up":
- **Election cycle** (select): 1 week nominations / 1 week voting; 2 weeks / 2 weeks; 2 weeks / 3 weeks; 2 weeks / 4 weeks.
- **Nominations start** (date and time picker).
- **Each phase starts at** and **ends at** (times, defaults 09:00 and 17:00).
- **Fill in the dates** button.

How the dates are worked out (**revised 31 October** after review):
1. **Visible from** is the same moment as **Nominations open** (the start date and time chosen).
2. Nominations close at the end time on the last day of the period (the day before the same weekday N weeks later, so Monday to Sunday).
3. **Candidates advertised** starts **5 minutes after nominations close**.
4. **Voting opens** at the start time (09:00) on the **day after the Candidates advertised date**.
5. Voting closes at the end time on the last day of its period.
6. Results are published **5 minutes after voting closes** (or at the next start time, "next morning", chosen in the panel).
7. **Visible until** is **12 weeks after the results are published** (a setting in the panel, default 12 weeks).
8. **Overlap guard:** if a calculated start would not be after the previous end, it moves forward in **5 minute steps** until the rule holds. Nothing moves backward.
9. The result is checked with the same rules as the form before it is written; the timeline preview and error markers then show the outcome.

**One rule changes.** Today nominations must start strictly *after* the visibility start (`getDateRules()`), so "Visible from = Nominations open" would be refused. The rule becomes "nominations may start at the same time as, or after, the visibility start" ("Start date must not be before visibility start date."). It changes in the PHP rule table (the form and the JavaScript read the same table), the tests and the docs. Nothing else depends on the strict version.

**Example timeline for review.** Settings: start Monday 1 March 2027 09:00, phases start 09:00 and end 17:00, results 5 minutes after voting closes, visible for 12 weeks after the results. Time zone `Australia/Sydney`.

| Date | 1 wk nominations / 1 wk voting | 2 wk / 2 wk | 2 wk / 3 wk | 2 wk / 4 wk |
|---|---|---|---|---|
| Visible from | Mon 1 Mar 09:00 | Mon 1 Mar 09:00 | Mon 1 Mar 09:00 | Mon 1 Mar 09:00 |
| Nominations open | Mon 1 Mar 09:00 | Mon 1 Mar 09:00 | Mon 1 Mar 09:00 | Mon 1 Mar 09:00 |
| Nominations close | Sun 7 Mar 17:00 | Sun 14 Mar 17:00 | Sun 14 Mar 17:00 | Sun 14 Mar 17:00 |
| Candidates advertised | Sun 7 Mar 17:05 | Sun 14 Mar 17:05 | Sun 14 Mar 17:05 | Sun 14 Mar 17:05 |
| Voting opens | Mon 8 Mar 09:00 | Mon 15 Mar 09:00 | Mon 15 Mar 09:00 | Mon 15 Mar 09:00 |
| Voting closes | Sun 14 Mar 17:00 | Sun 28 Mar 17:00 | Sun 4 Apr 17:00 | Sun 11 Apr 17:00 |
| Results published | Sun 14 Mar 17:05 | Sun 28 Mar 17:05 | Sun 4 Apr 17:05 | Sun 11 Apr 17:05 |
| Visible until | Sun 6 Jun 17:05 | Sun 20 Jun 17:05 | Sun 27 Jun 17:05 | Sun 4 Jul 17:05 |

Points the example shows:
- A "week" runs from the start time to the end time on the last day (Monday 09:00 to Sunday 17:00), not to the same time a week later.
- Candidates are advertised from Sunday 17:05, but voting opens Monday 09:00, so the advertising period is about 16 hours. That follows from the rules you gave.
- Choosing "next morning" for results: the 2 / 2 election's results move from Sun 28 Mar 17:05 to **Mon 29 Mar 09:00**, and Visible until to Mon 21 Jun 09:00.
- Sydney's clocks go back on Sunday 4 April 2027 (the 2 / 3 election closes that day). Times are kept as local clock times (17:00 stays 17:00).
- If a start time is not before the end time (for example 17:00 to 09:00), the panel refuses and explains. If the nominations start is not a Monday, the same rules apply from that weekday.

**Where the calculation lives.** One PHP function, `CRM_Elections_Helper_Dates::schedule(...)`, with an APIv4 action `Election::suggestDates` (needs `administer Elections`) the button calls. One source of truth, tested in PHPUnit (including Daylight Saving changes in `Australia/Sydney`), instead of a second copy in JavaScript.

**Behaviour.** If dates are already filled in, the button asks "This replaces the dates entered so far. Continue?". It warns if the start is in the past. It is only on the form, which an active election cannot open. The generated dates can still be edited by hand afterwards.

**Approved 31 October with the revisions above** (visible until 12 weeks after the results; visible from the same as nominations open; advertised 5 minutes after nominations close; voting opens the next day at 09:00).

## R8 – Celebration effects on the results page

**Proposal.**
- Display tab: a tick box **Display celebration effects on the Election results page** and, when ticked, **Effect** (select):
  1. **Confetti** – paper confetti shot from both lower corners.
  2. **Fireworks** – rockets and bursts over the page.
  3. **Balloons** – balloons floating up.
  4. **Golden sparkle** – a gold shimmer falling from the top (fits the Beekeeper test site, works for any).
  5. **Ticker tape and spotlight** – streamers with a spotlight sweep over the winners.
  6. **Surprise me** – a different effect for each election (picked once from the election id, so the page does not change on reload).
  A **Preview** button shows the effect over the form without saving.

- Results page only. The Election summary page does not celebrate (it is a reference page people revisit).

**Approved 31 October with the revision above:** no once-per-browser rule; shown for up to 5 days after the results are published, configurable per election. The "Play" option and the "Celebrate again" link are dropped (nothing to replay, it plays each visit).

Still as proposed: the five effects plus "Surprise me", default off.

**Tests.** Playwright on WordPress, Drupal and Joomla: canvas appears on every visit inside the window, is absent after the window (results date moved back), is absent under emulated reduced motion, and covers the theme header without blocking clicks. PHPUnit for the setting and the upgrade.

## R9 – Results page header logo, header text and footer text

**Problem to solve first.** The election form is locked once the election starts (`canEdit()`), but results are shown after it ends. These settings must stay editable until the results are published. So there are two entry points: the Display tab (before the election starts), and a **Results page** button on the Election overview (any time before results are published), which opens a small form with just these fields (and the R8 celebration fields). The pre-save guard (`CRM_Elections_Helper_Guard`) gets a short allow list of "display only" fields that may change while the election is active; they are audited like every other change.

**Proposal.**
- Fields: **Header logo** (upload), **Logo description** (alt text, required with a logo), **Header text**, **Footer text**.
- The page shows: logo and header text above the results, footer text below.
- **Text is plain text** (line breaks kept, everything escaped), not HTML, in line with the script-injection hardening in [12](../../../architecture/security.md). Limits: header 200 characters, footer 1000.
- **Logo upload:** PNG, JPEG, GIF or WebP up to 2 MB (no SVG, which can carry script); the real file type and size are checked, the image is re-encoded, and it is stored through CiviCRM's file table with the entity link to the election. Shown scaled to a maximum height of 120 px.
- **Serving the logo:** CiviCRM's own file URL needs a logged-in user. People on a personal link would see a broken image. A small public route `civicrm/elections/results-logo?eid=` streams the logo only when the results are published, with a cache header; it serves nothing else.
- **Schema:** `results_header_text` (VARCHAR 255), `results_footer_text` (TEXT), `results_logo_file_id` (INT UNSIGNED NULL, foreign key to `civicrm_file`, ON DELETE SET NULL), `results_logo_alt` (VARCHAR 255). Upgrade script, audit, Duplicate (copies the text and re-uses the logo file by copy).
- Applies to the results page. **Decision:** also on the Election summary page?

**Approved 31 October (all three recommendations).** Questions as asked:
1. Approve the two entry points (Display tab, and Results page button on the overview while the election is running)?
2. Plain text only, or basic formatting (bold, links) through a sanitised editor? *(Recommended: plain text.)*
3. Logo and header/footer on the summary page as well as the results page? *(Recommended: yes, same header and footer on both.)*

**Tests and docs.** PHPUnit (field limits, rejected file types, guard allow list, upgrade), Playwright (upload, appears for a logged-in person and for a personal-link visitor, not before the results are published) on all three CMSs. New doc page `admin_results_page.md`.

## R10 – Groups empty for an Elections Manager

**Verified on election-test, 31 October.** `bee.manager` (Margaret Doyle, role Elections Manager: `access CiviCRM`, `administer Elections`, `view Elections`, `access AJAX API`) gets **0 groups** from the Group API. Giving the role `view all contacts` returns all 4; `edit all contacts` also works; `edit groups` alone does not. This is CiviCRM core behaviour: which groups a person can see follows contact permissions (or ACLs). It is a documentation gap, and the form fails silently when it happens.

**Documentation failures found.**
- `docs/setup.md` lists permissions only for people who take part, not for organisers.
- `docs/setup.md` says staff "also need administer CiviCRM to see the Elections menu". The code says the Elections menu needs `access CiviCRM` and `administer Elections` only; `administer CiviCRM` is for the Elections Settings page. The document is wrong.
- Nothing says that choosing groups and finding candidates needs contact permissions, or that the message template link needs `edit message templates`.
- The Playwright manager role (`administer Elections` only) is not the real thing, which is why no test caught this.

**Proposal.**
1. **A permissions page** (`docs/setup.md` section, plus `docs/roles_and_permissions.md`) with a table by role, built from the route list in `xml/Menu/elections.xml` and checked against it:

   | Role | What they do | Permissions needed |
   |---|---|---|
   | Election organiser | Create and run elections | `access CiviCRM`, `administer Elections`, `access AJAX API`, **`view all contacts`** (or an ACL that lets them view the groups and the people), and for the template link `edit message templates` |
   | Site administrator | Settings, roles | `administer CiviCRM` (Elections Settings page) |
   | Person taking part (voter, nominator, nominee, candidate) | Nominate, accept, vote, see results | `view Elections`, `access AJAX API`, plus the profile and uploaded files permissions already documented |
   | Person using a personal link | Same, not logged in | Nothing; needs the election's non-logged-in setting and a valid link |
   | Results viewer | Read published results | Same as a person taking part |

   Each of WordPress, Drupal and Joomla gets its own wording for where to tick them.
2. **A notice on the form.** When the group list is empty and the user lacks `view all contacts`, the Participation tab says, above the group fields: "You cannot see any groups. Ask a site administrator to give your role the CiviCRM permission View All Contacts (or an ACL for the groups), then reload this page." (Same idea on the Candidates screen.)
3. **Tests.** The Playwright manager role is changed to exactly the documented organiser permissions, and a test proves groups can be chosen; another proves the notice appears when `view all contacts` is removed. A PHPUnit test checks that every `administer Elections` route is listed in the documented table.
4. **election-test site:** add `view all contacts` to the Elections Manager role in `provision/01-site.sh` once approved (today's behaviour stays visible until then if you want to review it).

**Alternative (needs your decision).** Let anyone with `administer Elections` list groups for the election form without `view all contacts`, using a small extension API that returns group titles only. It removes the extra permission for the groups, but organisers still need contact access to pick candidates, and it widens what an organiser can see beyond CiviCRM's own rules. *Not recommended;* documenting and warning is safer and matches CiviCRM's model.

**What the group-title alternative is.** Today the group pickers on the election form call CiviCRM's own Group API as the logged-in person, so CiviCRM applies its contact permissions and returns nothing to someone without `view all contacts`. The alternative would be a small API in this extension, say `ElectionGroup.getlist`, that needs only `administer Elections`, ignores CiviCRM's contact permissions, and returns just the id and title of each active, non-hidden group. The pickers would use it instead, so Margaret could choose groups without `view all contacts`. What it does *not* fix: the CiviCRM Manage Groups page would still say "None found", and finding people to add as candidates (and the other contact searches) would still need contact permissions. What it costs: an organiser would see the titles of groups that CiviCRM, or the site's ACLs, deliberately hide from them, and the extension would carry its own rule about what groups an organiser may see. That is why I do not recommend it. *(Recommended: no. Document the permissions and show the notice.)*

### Things worth knowing

- **Removing a mixin needs the mixin cache emptied.** While finding how to register the API field I enabled the `scan-classes` mixin and then removed it again; CiviCRM kept the cached list (`civicrm_cache` rows `mixinScan` and `mixinBoot`) and `cv flush` crashed on classes of optional integrations. Never shipped, only a development note.
- **The headless test database does not follow upgrades.** After a schema change the test database `civicrm_tests_dev` must be copied from the site database again (see [01](../../../environments/README.md)); CI builds it new each time.
- **Not verified in a browser by the tester:** the election-test site (the Chrome profile was not signed in and passwords are never typed by the tester). The Playwright suites cover WordPress; Drupal and Joomla runs are listed in [11](../../2.2/archive/roadmap.md).
